# EX-025-002 - Leçons architecturales

## Énoncé

Extrayez trois leçons architecturales de GShard pour un système MoE distribué.

## Ce que l'exercice vérifie

L'exercice vérifie que GShard n'est pas seulement un papier de modèle. C'est aussi une leçon de distribution, compilation et infrastructure.

## Solution détaillée

### 1. La modularité exige une infrastructure

Distribuer des experts demande plus que déclarer plusieurs modules. Il faut gérer :

- placement ;
- dispatch ;
- recombinaison ;
- capacité ;
- communication ;
- load balancing.

La modularité devient un problème système.

### 2. Le compilateur et le runtime comptent

GShard s'appuie sur un environnement où les annotations de sharding, le compilateur et le matériel travaillent ensemble. Une idée scalable dans cette pile ne se transpose pas automatiquement ailleurs.

Le modèle et l'infrastructure ne sont pas séparés.

### 3. Le routage doit être mesuré comme une charge

Le routeur ne choisit pas seulement un expert abstrait. Il crée une charge sur des devices réels. Il faut donc mesurer :

- tokens par expert ;
- charge par device ;
- communication ;
- latence ;
- tokens débordés.

## Points importants

- GShard montre le MoE comme système distribué.
- Le sharding est une décision d'architecture.
- Le compilateur devient un acteur du modèle.
- Le routeur crée une charge matérielle.
- La portabilité n'est pas automatique.

## Prolongement

Une bonne lecture de GShard pour un architecte est : avant d'ajouter des experts distribués, il faut savoir comment ils seront placés, appelés, mesurés et déplacés.
