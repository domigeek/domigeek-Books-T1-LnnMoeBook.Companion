# EX-025-005 - Portabilité

## Énoncé

Pourquoi une architecture efficace avec GShard, XLA et TPU ne se transpose-t-elle pas automatiquement dans une autre stack ?

## Ce que l'exercice vérifie

L'exercice vérifie que la performance d'un MoE distribué dépend fortement de la pile matérielle et logicielle.

## Solution détaillée

Une architecture efficace dans un environnement GShard, XLA et TPU bénéficie de choix spécifiques :

- compilateur capable d'optimiser le sharding ;
- topologie matérielle connue ;
- primitives collectives efficaces ;
- formats de tenseurs adaptés ;
- runtime conçu pour ce type de distribution.

Dans une autre stack, par exemple GPU avec un framework différent, les mêmes abstractions peuvent coûter plus cher.

Différences possibles :

- communication inter-GPU différente ;
- kernels moins optimisés ;
- all-to-all plus coûteux ;
- placement manuel nécessaire ;
- mémoire plus limitée ;
- outils de profiling différents ;
- support MoE moins mature.

Donc l'architecture conceptuelle peut inspirer, mais l'efficacité doit être revalidée.

## Points importants

- Le compilateur influence fortement la scalabilité.
- La topologie matérielle compte.
- Les primitives de communication changent selon la stack.
- Les kernels et formats ne sont pas toujours équivalents.
- La portabilité doit être testée.

## Prolongement

La bonne question n'est pas "peut-on copier GShard ?" mais "quels principes de GShard restent valables dans notre pile, et à quel coût ?".
