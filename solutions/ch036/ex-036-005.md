# EX-036-005 - Comparer routage top-1, top-2 et dense

## Énoncé

Utilisez `SparseMoeLayer` pour comparer le nombre d'évaluations d'experts entre `TopK = 1`, `TopK = 2` et `TopK = ExpertCount`.

## Ce que l'exercice vérifie

L'exercice vérifie que le routage sparse réduit le nombre d'experts évalués par token. Il ne vérifie pas à lui seul la latence réelle, car la latence dépend aussi du routeur, des copies mémoire, du regroupement des tokens et du matériel.

## Solution détaillée

Soit :

```text
T = nombre de tokens
E = nombre total d'experts
K = nombre d'experts actifs par token
```

Le nombre d'évaluations d'experts actives est :

```text
active_evaluations = T * K
```

Le nombre d'évaluations denses, si chaque token passait dans tous les experts, serait :

```text
dense_evaluations = T * E
```

Dans `SparseMoeLayer`, ces deux valeurs sont exposées dans le résultat :

```text
ActiveExpertEvaluations
DenseExpertEvaluations
```

Un test ou petit programme peut donc exécuter le même batch avec trois valeurs de `TopK`.

```csharp
var batch = SparseMoeLayer.GenerateSyntheticBatch(tokensPerClass: 8);

foreach (var topK in new[] { 1, 2, 4 })
{
    var options = SparseMoeLayerOptions.Default with
    {
        ExpertCount = 4,
        TopK = topK
    };

    var result = SparseMoeLayer.Forward(batch, options);

    Console.WriteLine(
        $"TopK={topK} active={result.ActiveExpertEvaluations} dense={result.DenseExpertEvaluations}");
}
```

Si `tokensPerClass = 8` et `ClassCount = 4`, alors `T = 32`. Avec `E = 4`, on obtient :

| Routage | Formule | Évaluations actives | Évaluations denses | Ratio actif/dense |
|---|---:|---:|---:|---:|
| Top-1 | `T * 1` | `32` | `128` | `25 %` |
| Top-2 | `T * 2` | `64` | `128` | `50 %` |
| Dense | `T * 4` | `128` | `128` | `100 %` |

Le cas `TopK = ExpertCount` n'est plus vraiment sparse. Il sert de référence dense : tous les experts sont actifs pour tous les tokens.

Cette comparaison explique pourquoi les MoE sont attirants à grande échelle. On peut augmenter le nombre total de paramètres en ajoutant des experts, tout en activant seulement une fraction des experts par token. Mais il faut immédiatement ajouter la nuance d'ingénierie : réduire le nombre d'évaluations ne garantit pas automatiquement une réduction de latence.

Dans un système réel, il faut aussi mesurer :

- la distribution de charge par expert ;
- le coût du routeur ;
- le coût de dispatch des tokens ;
- le coût de communication si les experts sont distribués ;
- le taux de tokens refusés ou débordés si une capacité est imposée ;
- la qualité de sortie.

## Critères d'acceptation

La solution est correcte si elle :

- utilise le même batch pour les trois configurations ;
- garde le même `ExpertCount` ;
- varie seulement `TopK` ;
- affiche `ActiveExpertEvaluations` et `DenseExpertEvaluations` ;
- explique que `TopK = ExpertCount` correspond à une référence dense ;
- évite de conclure que le plus sparse est automatiquement le meilleur.

## Points importants

Le routage top-1 est moins coûteux en évaluations, mais plus brutal : un seul expert reçoit le token. Le top-2 coûte plus cher, mais permet une combinaison de deux expertises. Le dense est simple conceptuellement, mais perd l'intérêt computationnel du MoE.

## Prolongement

Un bon prolongement consiste à ajouter la qualité de classification et la perte d'équilibrage de charge. On peut alors observer le compromis entre coût, spécialisation et stabilité du routage.
