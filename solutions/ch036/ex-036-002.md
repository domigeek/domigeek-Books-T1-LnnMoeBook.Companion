# EX-036-002 - Créer un benchmark pédagogique

## Énoncé

Définissez un benchmark comparant MLP, RNN, LTC et MoE sur des tailles d'entrée contrôlées.

## Ce que l'exercice vérifie

L'exercice vérifie que comparer des architectures demande un protocole. Un benchmark utile ne consiste pas à lancer quatre exemples au hasard et à publier le temps le plus flatteur. Il faut contrôler les dimensions, le nombre d'itérations, le warmup, le runtime, les métriques et les limites de l'interprétation.

## Solution détaillée

Le benchmark doit répondre à une question précise :

```text
À taille d'entrée contrôlée, quel est le coût relatif d'une passe avant
et d'une petite boucle d'entraînement pour quatre familles d'exemples ?
```

On ne cherche pas à prouver qu'une architecture est meilleure. On cherche à mesurer ce que le dépôt compagnon exécute réellement sur une machine donnée.

Un protocole minimal :

| Élément | Choix proposé |
|---|---|
| Langage | C# |
| Runtime | .NET |
| Backend | TorchSharp quand l'exemple l'utilise |
| Mesure | temps moyen, écart type, allocations, perte initiale et finale si entraînement |
| Warmup | 3 à 5 exécutions ignorées |
| Répétitions | 20 à 50 selon le coût |
| Tailles | petite, moyenne, grande |
| Seed | déterministe |
| Sortie | tableau Markdown ou CSV |

Les tailles peuvent être définies ainsi :

| Profil | Batch | Longueur séquence | Largeur entrée | Experts | TopK |
|---|---:|---:|---:|---:|---:|
| Petit | 16 | 8 | 8 | 4 | 1 |
| Moyen | 64 | 32 | 32 | 8 | 2 |
| Grand | 128 | 64 | 64 | 16 | 2 |

Pour rester honnête, chaque architecture ne manipule pas exactement les mêmes objets. Un MLP ne déroule pas le temps. Un RNN et un LTC ont une dynamique séquentielle. Un MoE ajoute un routeur et des experts. Le benchmark doit donc comparer des coûts d'exécution sous contraintes communes, pas prétendre que les tâches sont identiques.

Une structure de benchmark pourrait être :

```text
benchmarks/
  csharp/
    LnnMoeBook.Benchmarks/
      Program.cs
      BenchmarkProfiles.cs
      MlpBenchmarks.cs
      RnnBenchmarks.cs
      LtcBenchmarks.cs
      MoeBenchmarks.cs
      BenchmarkResult.cs
      reports/
        benchmark-summary.csv
        benchmark-summary.md
```

Si le projet utilise BenchmarkDotNet, chaque classe peut exposer des méthodes annotées :

```csharp
[MemoryDiagnoser]
public class LtcBenchmarks
{
    private SimpleLtcCell.LtcSequenceDataset? _dataset;
    private SimpleLtcCell.LtcCellParameters? _parameters;

    [Params(16, 64, 128)]
    public int SequenceCount { get; set; }

    [Params(8, 32, 64)]
    public int SequenceLength { get; set; }

    [GlobalSetup]
    public void Setup()
    {
        _dataset = SimpleLtcCell.GenerateSyntheticSequences(
            SequenceCount,
            SequenceLength,
            SimpleLtcCell.LtcSimulationOptions.Default);

        _parameters = SimpleLtcCell.LtcCellParameters.CreateStudent();
    }

    [Benchmark]
    public float ForwardOnly()
    {
        var loss = SimpleLtcCell.MeanSquaredError(
            _dataset!,
            _parameters!,
            SimpleLtcCell.LtcSimulationOptions.Default);

        return loss;
    }
}
```

Pour le MoE, il faut mesurer au moins deux signaux :

```text
temps_forward
active_expert_evaluations
dense_expert_evaluations
load_balancing_loss
```

Cette partie est importante. Un MoE peut afficher un coût théorique plus bas grâce au routage sparse, mais le routeur, les copies mémoire et les regroupements de tokens peuvent coûter cher. Un benchmark pédagogique doit donc montrer le coût visible, pas seulement le nombre d'experts activés.

La sortie attendue peut ressembler à ceci :

| Modèle | Profil | Temps moyen | Allocations | Signal qualité | Remarque |
|---|---|---:|---:|---|---|
| MLP | petit | `x ms` | `y KB` | loss finale | baseline dense |
| RNN | petit | `x ms` | `y KB` | loss finale | coût séquentiel |
| LTC | petit | `x ms` | `y KB` | loss finale | coût solveur |
| MoE | petit | `x ms` | `y KB` | accuracy/loss | coût routeur + experts |

## Critères d'acceptation

Un benchmark acceptable doit :

- compiler sans configuration cachée ;
- indiquer la machine, le runtime et le backend ;
- utiliser les mêmes profils de taille ;
- séparer warmup et mesure ;
- produire une sortie lisible ;
- éviter les conclusions générales non démontrées ;
- documenter les limites de comparaison.

## Points importants

Le benchmark doit être pédagogique avant d'être spectaculaire. S'il montre que le LTC est plus coûteux qu'un RNN simple dans un cas donné, ce n'est pas un échec. C'est une information utile. Si le MoE active moins d'experts mais ne réduit pas la latence sur CPU, c'est également une information utile.

## Prolongement

Une version plus avancée pourrait séparer CPU et GPU, mesurer la variance, exporter les résultats en JSON et produire automatiquement une figure. Mais la première version doit rester simple : dimensions contrôlées, exécution reproductible, interprétation prudente.
