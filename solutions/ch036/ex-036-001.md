# EX-036-001 - Ajouter des tests unitaires à la cellule LTC

## Énoncé

Ajoutez ou proposez trois tests supplémentaires pour `SimpleLtcCell` : un test de shape, un test de constante temporelle et un test de perte décroissante.

## Ce que l'exercice vérifie

L'exercice vérifie que l'on ne teste pas une cellule LTC seulement avec une sortie numérique quelconque. Il faut vérifier le contrat des tenseurs, le comportement liquide de la constante temporelle et la capacité minimale d'apprentissage sur un problème synthétique.

## Solution détaillée

Une cellule LTC pédagogique doit rester petite, mais ses tests doivent couvrir trois familles de problèmes.

La première famille concerne les formes de tenseurs. Beaucoup de bogues en apprentissage profond ne viennent pas d'une équation fausse, mais d'un axe inversé. Une séquence peut être représentée comme `(batch, time, features)` ou `(time, batch, features)`. Les deux conventions existent. Le test doit donc fixer clairement la convention utilisée par l'exemple.

Dans le dépôt, `LtcSequenceDataset` expose trois conversions utiles :

```text
Inputs     -> (sequenceCount, sequenceLength, 1)
DeltaTimes -> (sequenceCount, sequenceLength)
Targets    -> (sequenceCount, 1)
```

Un test de shape peut ressembler à ceci :

```csharp
[Fact]
public void DatasetTensorViewsKeepExpectedShapes()
{
    using var dataset = SimpleLtcCell.GenerateSyntheticSequences(
        sequenceCount: 12,
        sequenceLength: 6,
        SimpleLtcCell.LtcSimulationOptions.Default);

    using var inputs = dataset.ToInputTensor();
    using var deltaTimes = dataset.ToDeltaTimeTensor();
    using var targets = dataset.ToTargetTensor();

    Assert.Equal(new long[] { 12, 6, 1 }, inputs.shape);
    Assert.Equal(new long[] { 12, 6 }, deltaTimes.shape);
    Assert.Equal(new long[] { 12, 1 }, targets.shape);
}
```

Le but n'est pas seulement de vérifier TorchSharp. Le but est de protéger le contrat pédagogique de l'exemple. Si une future modification inverse `sequenceCount` et `sequenceLength`, le modèle peut encore compiler, mais l'interprétation des données devient fausse.

Le deuxième test concerne la constante temporelle. Dans une cellule LTC, la constante temporelle effective ne doit pas être traitée comme un hyperparamètre figé. Elle dépend de l'état et de l'entrée. Le test doit donc vérifier que deux entrées différentes peuvent produire deux constantes temporelles effectives différentes.

Un test robuste :

```csharp
[Fact]
public void EffectiveTimeConstantDependsOnInput()
{
    var parameters = SimpleLtcCell.LtcCellParameters.CreateStudent();

    var lowInput = SimpleLtcCell.ComputeStateProperties(
        parameters,
        input: -1.0f,
        state: 0.1f);

    var highInput = SimpleLtcCell.ComputeStateProperties(
        parameters,
        input: 1.0f,
        state: 0.1f);

    Assert.InRange(lowInput.Gate, 0.0f, 1.0f);
    Assert.InRange(highInput.Gate, 0.0f, 1.0f);
    Assert.True(lowInput.EffectiveTimeConstant > 0.0f);
    Assert.True(highInput.EffectiveTimeConstant > 0.0f);
    Assert.NotEqual(lowInput.EffectiveTimeConstant, highInput.EffectiveTimeConstant);
}
```

Si les paramètres choisis garantissent une direction précise, on peut être plus strict. Par exemple, si une entrée plus élevée ouvre davantage la porte de conductance, la constante temporelle effective peut diminuer. Mais pour un exemple pédagogique, le plus important est d'éviter un test fragile qui impose une propriété non expliquée dans le chapitre.

Le troisième test vérifie que l'entraînement réduit la perte sur un jeu synthétique déterministe. Il ne prouve pas que le modèle généralise. Il prouve seulement que la boucle d'optimisation, le calcul de perte et l'estimation de gradient ne sont pas cassés.

```csharp
[Fact]
public void TrainingReducesLossOnSyntheticSequences()
{
    using var dataset = SimpleLtcCell.GenerateSyntheticSequences(
        sequenceCount: 32,
        sequenceLength: 7,
        SimpleLtcCell.LtcSimulationOptions.Default);

    var report = SimpleLtcCell.Train(
        dataset,
        SimpleLtcCell.LtcCellParameters.CreateStudent(),
        SimpleLtcCell.LtcTrainingOptions.Default,
        SimpleLtcCell.LtcSimulationOptions.Default);

    Assert.True(report.FinalLoss < report.InitialLoss);
    Assert.NotEmpty(report.LossHistory);
    Assert.All(report.LossHistory, loss => Assert.True(float.IsFinite(loss)));
}
```

Ce test ne doit pas exiger une perte finale universelle trop basse. Une valeur absolue trop stricte rendrait le test dépendant de détails d'initialisation, de runtime ou de précision. Pour un exemple de livre, le signal attendu est plus simple : la perte descend, elle reste finie, et l'historique contient assez de points pour être inspecté.

## Points importants

- Le test de shape protège le contrat d'entrée et de sortie.
- Le test de constante temporelle protège l'idée centrale d'une cellule liquide.
- Le test de perte décroissante protège la boucle d'entraînement.
- Un test pédagogique doit être stable, lisible et relié au mécanisme présenté dans le chapitre.
- Il ne faut pas transformer un exemple minimal en banc d'essai scientifique.

## Prolongement

Une suite plus complète pourrait ajouter un test comparant Euler et RK4 sur la stabilité numérique, un test d'options invalides et un test de sérialisation des paramètres. Mais ces ajouts doivent rester au service de la compréhension : un dépôt compagnon n'est pas un framework de recherche complet.
