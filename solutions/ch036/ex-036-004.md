# EX-036-004 - Documenter les shapes

## Énoncé

Choisissez un exemple du dépôt et documentez toutes les formes de tenseurs qu'il manipule.

## Ce que l'exercice vérifie

L'exercice vérifie une compétence très concrète : savoir lire un exemple neuronal comme un contrat de dimensions. Les équations donnent l'idée, mais les shapes disent si le code peut réellement tourner.

## Solution détaillée

Prenons l'exemple `SparseMoeLayer`. Il est intéressant parce qu'il combine trois choses : des tokens, un routeur et plusieurs experts. Cela force à distinguer la dimension batch, la dimension expert et la dimension classe.

Les paramètres principaux sont :

| Nom | Sens |
|---|---|
| `T` | nombre de tokens dans le batch |
| `F` | largeur des features d'entrée |
| `E` | nombre d'experts |
| `K` | nombre d'experts actifs par token |
| `C` | nombre de classes ou logits de sortie |

Dans l'exemple synthétique, `FeatureWidth` vaut souvent `2`, `ClassCount` vaut `4`, et `ExpertCount` peut valoir `4` par défaut. Le nombre de tokens dépend de la taille de batch générée.

Le contrat de dimensions peut être écrit ainsi :

| Objet | Shape logique | Rôle |
|---|---:|---|
| `Features` | `(T, F)` | entrée de chaque token |
| `Labels` | `(T)` | classe attendue par token |
| scores du routeur | `(T, E)` | score de routage pour chaque expert |
| poids top-k | `(T, K)` | poids des experts actifs |
| indices top-k | `(T, K)` | identifiants des experts actifs |
| logits par expert | `(T, E, C)` | sortie potentielle de chaque expert |
| logits combinés | `(T, C)` | sortie agrégée après routage |
| probabilités | `(T, C)` | distribution prédite |
| charge par expert | `(E)` | nombre ou masse de tokens par expert |

Le flux de données est :

```text
features(T,F)
  -> router
  -> scores(T,E)
  -> topk indices(T,K), weights(T,K)
  -> experts
  -> expert logits(T,E,C)
  -> weighted combine
  -> logits(T,C)
```

La partie la plus sensible est la combinaison pondérée. Pour chaque token `t`, on ne veut pas additionner tous les experts de manière dense si le routage est sparse. On veut calculer :

```text
output[t] = somme_{j=1..K} weight[t,j] * expert_output[t, expert_index[t,j]]
```

La shape finale doit donc redevenir `(T, C)`. Si elle devient `(T, K, C)`, l'agrégation n'a pas été faite. Si elle devient `(E, C)`, la dimension token a été perdue. Si elle devient `(T, E)`, les classes ont été confondues avec les experts.

Un commentaire utile dans le code ou dans une solution peut être :

```text
Ne jamais lire ExpertCount comme une dimension de sortie métier.
Les experts sont une dimension de calcul interne. La sortie métier reste ClassCount.
```

Dans un modèle réel, cette discipline devient encore plus importante. Un MoE dans un Transformer peut manipuler des tenseurs de forme `(batch, sequence, hidden)`. Avant le routage, on a souvent une vue aplatie `(batch * sequence, hidden)`. Après le passage dans les experts, il faut restaurer la forme originale ou au moins garantir que l'ordre des tokens est préservé.

## Erreurs fréquentes

- Confondre `K` et `E`.
- Perdre l'ordre des tokens pendant le dispatch.
- Agréger les experts avant d'avoir appliqué les bons poids.
- Interpréter la charge des experts comme une sortie du modèle.
- Comparer deux modèles sans vérifier que leurs dimensions d'entrée sont réellement identiques.

## Points importants

Documenter les shapes n'est pas de la paperasse. C'est une manière de rendre l'architecture débogable. Dans les systèmes neuronaux, une shape fausse peut produire une erreur immédiate, mais elle peut aussi produire un résultat numérique plausible et complètement mal interprété.

## Prolongement

Le même travail peut être fait pour `SimpleLtcCell`. On y verrait une autre famille de dimensions : batch, temps, entrée scalaire, état caché scalaire et cible finale. C'est un bon exercice pour comparer une architecture temporelle et une architecture à routage.
