# EX-004-001 - Identifier l'état minimal

## Énoncé

Choisissez un système réel que vous connaissez : cache applicatif, file de messages, session utilisateur, robot, monitoring de serveur ou série temporelle métier. Décrivez les variables d'état minimales nécessaires pour prédire son évolution immédiate.

## Ce que l'exercice vérifie

L'exercice vérifie la notion d'état. Un état utile n'est pas une copie complète du passé. C'est un résumé suffisant pour prédire l'évolution immédiate du système selon le niveau de détail recherché.

En architecture logicielle, cette distinction est très concrète. Stocker tout le passé coûte cher. Stocker trop peu rend le système aveugle.

## Solution détaillée

Prenons une file de messages.

On veut prédire son évolution immédiate, par exemple savoir si elle risque de se vider, de se stabiliser ou de s'accumuler dans les prochaines minutes.

Un état minimal pourrait contenir :

```text
queue_length
incoming_rate
processing_rate
consumer_count
average_processing_time
retry_rate
dead_letter_rate
oldest_message_age
```

### Variables d'état

`queue_length` indique combien de messages sont en attente. C'est la photographie la plus évidente du système.

`incoming_rate` indique combien de messages arrivent par unité de temps. Une file de 100 messages n'a pas le même sens si 1 message arrive par seconde ou si 10 000 messages arrivent par seconde.

`processing_rate` indique combien de messages sont traités par unité de temps. C'est la capacité effective, pas seulement la capacité théorique.

`consumer_count` indique combien de consommateurs travaillent. Si un consommateur tombe, la dynamique change.

`average_processing_time` donne une idée du coût de traitement. Une hausse brutale peut annoncer un problème en aval.

`retry_rate` indique la proportion de messages qui reviennent dans la file après échec. C'est important, car les retries peuvent amplifier la charge.

`dead_letter_rate` indique les messages qui sortent du flux normal vers une file d'erreur.

`oldest_message_age` mesure l'âge du plus vieux message. Deux files peuvent avoir la même longueur mais pas la même gravité opérationnelle.

### Entrées et sorties

Il faut distinguer l'état des entrées.

Entrées possibles :

```text
nouveaux messages
nouveaux consommateurs
configuration de retry
limites de débit
état du service aval
```

Sorties possibles :

```text
messages traités
messages échoués
latence observée
alertes
```

L'état n'est donc pas "tout ce qui existe". C'est ce que le système doit retenir à un instant pour expliquer son évolution.

### Équation intuitive

Une approximation très simple serait :

```text
queue_length_next = queue_length + incoming_rate * dt - processing_rate * dt + retries
```

Ce n'est pas un modèle complet, mais il force à nommer les variables.

## Points importants

- L'état minimal dépend de la prédiction demandée.
- Une file de messages ne se comprend pas seulement par sa longueur.
- Les taux d'arrivée et de traitement définissent la dynamique.
- Les retries peuvent transformer un petit incident en accumulation.
- Le plus vieux message est souvent plus parlant que la moyenne.

## Prolongement

Le même exercice peut être refait pour un réseau neuronal récurrent. Son état caché devrait résumer ce qui est utile pour la suite. La différence est que, dans un RNN, cet état est latent et appris. Dans une file de messages, on peut souvent le rendre explicite et observable. C'est une bonne raison de ne pas mystifier la notion d'état.
