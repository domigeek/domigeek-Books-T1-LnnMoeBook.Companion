# EX-029-005 - Placer Transformer² dans une architecture modulaire

## Énoncé

Imaginez une architecture qui utilise un modèle adapté dynamiquement à la Transformer² à l'intérieur d'un orchestrateur modulaire. Où placeriez-vous le dispatch de tâche, la mémoire, les experts externes et les logs ?

## Ce que l'exercice vérifie

L'exercice vérifie la séparation des responsabilités. Une adaptation interne du modèle ne doit pas absorber toute l'architecture système.

## Solution détaillée

Une organisation propre pourrait être :

```text
requête
  -> orchestrateur système
      -> classification de tâche
      -> politique de permissions
      -> récupération mémoire/RAG si nécessaire
      -> choix d'outils ou experts externes
      -> appel du modèle avec adaptation dynamique
      -> validation
      -> logs et métriques
  -> réponse
```

### Dispatch de tâche

Le dispatch global devrait rester au niveau de l'orchestrateur.

Il décide :

- type de tâche ;
- budget ;
- outils autorisés ;
- mémoire utilisable ;
- besoin de modèle adapté ;
- stratégie de fallback.

Le modèle peut avoir un dispatch interne pour son adaptation, mais il ne devrait pas décider seul des droits système.

### Mémoire

La mémoire persistante reste au niveau système :

```text
RAG
profil
documents
historique versionné
graphe de connaissances
```

Le modèle adapté reçoit un contexte sélectionné. Il ne devient pas lui-même la mémoire gouvernée.

### Experts externes

Les experts externes restent orchestrés explicitement :

```text
analyseur de code
moteur de recherche
outil de test
simulateur
service métier
```

Le modèle peut suggérer un besoin, mais l'orchestrateur applique les politiques d'appel, permissions et budgets.

### Logs

Les logs doivent couvrir :

- requête ;
- classification de tâche ;
- choix d'adaptation ;
- documents récupérés ;
- outils appelés ;
- coûts ;
- latence ;
- erreurs ;
- version du modèle ;
- résultat de validation.

Il faut éviter de se contenter d'un texte de raisonnement. Les traces opérationnelles doivent être structurées.

## Points importants

- Transformer² peut rester une brique interne du modèle.
- L'orchestrateur garde le dispatch système.
- La mémoire persistante reste gouvernée hors modèle.
- Les experts externes doivent avoir des contrats explicites.
- Les logs doivent être structurés et auditables.

## Prolongement

Cette séparation protège l'architecture. Si l'adaptation interne change, on peut encore garder les politiques, la mémoire, les outils et les logs stables. C'est exactement le genre de frontière qui rend un système maintenable.
