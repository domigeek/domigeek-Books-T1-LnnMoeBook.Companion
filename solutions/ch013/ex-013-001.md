# EX-013-001 - Identifier une limite du discret

## Énoncé

Donnez un exemple de système où deux séquences avec le même ordre d'événements n'ont pas la même signification parce que les délais sont différents.

## Ce que l'exercice vérifie

L'exercice vérifie une limite du temps discret naïf : l'ordre ne suffit pas toujours. Deux événements peuvent apparaître dans le même ordre, mais raconter deux histoires différentes selon les délais entre eux.

## Solution détaillée

Prenons un système de monitoring applicatif.

Séquence A :

```text
CPU élevé -> erreurs HTTP 500 -> redémarrage service
```

Les événements arrivent en 10 secondes.

Séquence B :

```text
CPU élevé -> erreurs HTTP 500 -> redémarrage service
```

Les mêmes événements arrivent sur 6 heures.

L'ordre est identique, mais la signification opérationnelle change.

Dans la séquence A, on peut soupçonner une cascade rapide : saturation, échec, redémarrage. Le délai court suggère une relation dynamique forte ou au moins une crise concentrée.

Dans la séquence B, le CPU élevé peut être un pic isolé, les erreurs peuvent venir d'un autre incident, et le redémarrage peut être une maintenance planifiée. L'ordre seul risque de créer une association trompeuse.

Un modèle qui ne voit que :

```text
[CPU élevé, erreurs 500, redémarrage]
```

perd l'information :

```text
10 secondes ou 6 heures ?
```

C'est précisément le problème. Dans plusieurs systèmes réels, le délai fait partie du signal.

## Points importants

- Même ordre ne veut pas dire même dynamique.
- Le délai entre événements peut changer l'interprétation.
- Les logs, capteurs, transactions et comportements utilisateur sont sensibles au temps réel.
- Une représentation purement discrète peut perdre cette information.

## Prolongement

Une première correction simple consiste à ajouter `Delta t` comme feature. Une correction plus structurée consiste à utiliser une architecture qui modélise explicitement l'évolution temporelle.
