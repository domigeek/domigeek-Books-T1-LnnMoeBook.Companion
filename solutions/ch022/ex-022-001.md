# EX-022-001 - Décomposer une tâche

## Énoncé

Choisissez une tâche technique, par exemple analyse de logs, génération de code ou classification de séries temporelles. Proposez trois à cinq experts possibles et justifiez chaque expert.

## Ce que l'exercice vérifie

L'exercice vérifie une décomposition raisonnée. Un expert doit avoir une responsabilité utile, pas seulement un nom élégant.

## Solution détaillée

Prenons l'analyse de logs applicatifs.

Experts possibles :

| Expert | Rôle | Entrées typiques | Métriques |
|---|---|---|---|
| Expert erreurs HTTP | Détecter motifs 4xx/5xx | codes, endpoints, taux d'erreur | rappel incidents HTTP |
| Expert latence | Suivre p95, p99, timeouts | latence, timeout, retries | délai de détection |
| Expert ressources | Relier CPU, mémoire, I/O | métriques serveur | faux positifs système |
| Expert séquence | Lire l'ordre d'événements | événements horodatés | qualité sur scénarios longs |
| Expert contexte déploiement | Identifier changements récents | version, release, config | attribution aux releases |

Cette décomposition peut aider si les sous-problèmes ont des régimes différents. Les erreurs HTTP ne se lisent pas comme une dérive mémoire lente. Un expert spécialisé peut mieux capter un type de signal.

Risques :

- experts redondants ;
- expert jamais utilisé ;
- routage instable ;
- perte d'information globale ;
- coût d'orchestration trop élevé.

Validation :

- utilisation par expert ;
- qualité par type d'incident ;
- ablations ;
- comparaison avec modèle dense ;
- latence et coût.

## Points importants

- Les experts doivent correspondre à des responsabilités mesurables.
- La décomposition doit être justifiée par la donnée.
- Les métriques par expert sont nécessaires.
- La redondance peut coûter cher.
- Un MoE doit battre une baseline plus simple.

## Prolongement

Une mauvaise décomposition ressemble à une architecture logicielle avec trop de microservices : beaucoup de frontières, peu de valeur, beaucoup de coordination.
