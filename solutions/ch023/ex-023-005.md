# EX-023-005 - Observabilité du routeur

## Énoncé

Proposez un tableau de bord minimal pour surveiller un routeur MoE en production.

## Ce que l'exercice vérifie

L'exercice vérifie que le routage doit être observable. Un MoE peut se dégrader sans erreur visible si le routeur change de comportement.

## Solution détaillée

Un tableau de bord minimal devrait contenir :

| Métrique | Rôle |
|---|---|
| Tokens par expert | Voir la distribution de charge |
| Utilisation par expert | Identifier experts morts ou saturés |
| Entropie du routeur | Mesurer diversité ou collapse |
| Tokens débordés/rejetés | Voir les limites de capacité |
| Latence par expert | Détecter hot spots |
| Coût de dispatch | Mesurer overhead du routage |
| Loss d'équilibrage | Suivre l'entraînement |
| Qualité par sous-domaine | Savoir si le routage aide vraiment |
| Dérive temporelle | Voir si le routeur change en production |

Il faut aussi conserver des vues par couche si le MoE apparaît dans plusieurs blocs.

Alertes utiles :

- un expert reçoit plus de `x %` des tokens ;
- un expert reçoit presque zéro token ;
- taux de débordement au-dessus d'un seuil ;
- latence p95 par expert trop élevée ;
- dérive forte par rapport à la semaine précédente.

## Points importants

- Observer seulement la loss globale ne suffit pas.
- Il faut mesurer routage, charge, latence et qualité.
- Les métriques doivent être suivies dans le temps.
- Les alertes doivent distinguer incident système et dérive modèle.
- La comparaison avec une baseline dense reste utile.

## Prolongement

Un routeur MoE ressemble à un composant de production critique. S'il est aveugle, tout le modèle devient difficile à opérer.
