# EX-021-002 - Capacité totale vs coût actif

## Énoncé

Expliquez pourquoi les MoE redeviennent importants dans les grands modèles.

## Ce que l'exercice vérifie

L'exercice vérifie le compromis central des MoE modernes : augmenter la capacité totale sans augmenter proportionnellement le calcul actif par token.

## Solution détaillée

Dans un modèle dense, chaque token traverse généralement les mêmes paramètres actifs. Si on augmente fortement la taille du modèle, on augmente souvent aussi le coût de calcul par token.

Un MoE sparse change ce compromis. Le modèle peut contenir beaucoup d'experts, donc beaucoup de paramètres au total, mais n'en activer qu'un petit nombre pour chaque token.

Exemple :

```text
64 experts disponibles
2 experts actifs par token
```

Le modèle possède une grande capacité stockée, mais le calcul actif par token reste limité aux experts sélectionnés.

C'est intéressant pour les grands modèles parce que la capacité totale peut aider à représenter plus de régimes, de langues, de styles ou de transformations internes. Mais le coût actif reste plus contrôlé qu'un modèle dense équivalent.

Le revers est système :

- il faut router les tokens ;
- équilibrer la charge ;
- éviter que certains experts soient saturés ;
- gérer la communication entre devices ;
- mesurer les tokens rejetés ou débordés ;
- maintenir la latence.

Donc les MoE redeviennent importants parce qu'ils proposent un compromis d'échelle. Ils ne suppriment pas le coût. Ils déplacent une partie du problème vers le routage et l'infrastructure.

## Points importants

- Capacité totale : tous les paramètres stockés.
- Coût actif : paramètres réellement utilisés pour un token.
- Les MoE peuvent augmenter la capacité sans coût actif proportionnel.
- Le routage devient une décision modèle et système.
- Les gains dépendent fortement de l'implémentation.

## Prolongement

Un MoE n'est pas automatiquement plus efficace. Il faut mesurer qualité, latence, mémoire, communication, charge par expert et coût par requête.
