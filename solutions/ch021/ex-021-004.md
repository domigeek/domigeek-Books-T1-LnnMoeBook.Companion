# EX-021-004 - Mauvaise interprétation de la spécialisation

## Énoncé

Pourquoi est-il dangereux de dire trop vite qu'un expert est "l'expert code" ou "l'expert math" ?

## Ce que l'exercice vérifie

L'exercice vérifie la prudence interprétative. Une régularité de routage n'est pas automatiquement une spécialisation humaine lisible.

## Solution détaillée

Si on observe qu'un expert reçoit souvent des entrées contenant du code, on peut conclure une seule chose de façon prudente :

```text
le routeur associe souvent certaines entrées contenant du code à cet expert dans ce contexte d'observation.
```

On ne peut pas conclure immédiatement :

```text
cet expert comprend le code
cet expert est l'expert code
cet expert est toujours responsable du code
```

Plusieurs explications sont possibles :

- l'expert capte une structure syntaxique ;
- il capte une distribution de tokens ;
- il est utilisé seulement dans certaines couches ;
- il dépend d'une seed ou d'un checkpoint ;
- il reçoit du code parce qu'un autre expert est saturé ;
- la régularité disparaît hors distribution.

Pour valider une spécialisation, il faudrait :

- logs de routage par couche ;
- comparaison sur plusieurs datasets ;
- ablations d'experts ;
- mesure de qualité quand l'expert est masqué ;
- stabilité sur plusieurs seeds ;
- contre-exemples ;
- comparaison avec modèle dense.

## Points importants

- Routage fréquent ne prouve pas spécialisation sémantique.
- Les experts ne doivent pas être anthropomorphisés.
- La spécialisation peut être locale à une couche.
- Il faut des ablations et des tests contrôlés.
- Une interprétation séduisante peut être fausse.

## Prolongement

Le langage le plus sûr est : "cet expert est souvent activé pour ce type d'entrée dans ces conditions". C'est moins spectaculaire, mais beaucoup plus solide.
