# EX-034-004 - Plan de rollback agentique

## Énoncé

Un agent de support a commencé à écrire en mémoire persistante après une nouvelle version. Décrivez un plan de rollback.

## Ce que l'exercice vérifie

L'exercice vérifie qu'un rollback agentique doit traiter le modèle et les écritures produites, pas seulement redéployer un ancien binaire.

## Solution détaillée

Étapes :

1. Geler immédiatement les nouvelles écritures mémoire.
2. Identifier la version fautive : modèle, prompt, politique, outil, schéma mémoire.
3. Restaurer la version précédente du modèle ou de l'orchestrateur.
4. Isoler toutes les écritures produites depuis le déploiement.
5. Marquer ces écritures comme `quarantined`.
6. Rejouer un échantillon de sessions avec l'ancienne version.
7. Comparer les écritures attendues et les écritures fautives.
8. Supprimer, invalider ou corriger les entrées fautives.
9. Documenter l'incident.
10. Remettre l'écriture mémoire avec garde-fou renforcé.

Traces nécessaires :

```text
memoryId
createdAt
agentVersion
promptVersion
sourceConversation
policyVersion
content
confidence
reviewStatus
```

Communication :

- prévenir l'équipe support ;
- indiquer la fenêtre touchée ;
- lister les données invalidées ;
- publier un runbook de vérification.

## Points importants

- Le rollback doit inclure la mémoire.
- Les écritures fautives doivent être isolées.
- Le replay aide à comprendre l'écart.
- Les versions modèle, prompt et politique sont toutes pertinentes.
- Il faut un runbook, pas seulement une commande.

## Prolongement

Une mémoire persistante sans journal d'écriture rend ce rollback presque impossible. C'est exactement pourquoi la gouvernance doit être conçue avant l'incident.
