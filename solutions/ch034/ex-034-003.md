# EX-034-003 - Model card simplifiée

## Énoncé

Rédigez une model card courte pour un classifieur de tickets support.

## Ce que l'exercice vérifie

L'exercice vérifie qu'un modèle doit être documenté selon son usage, ses limites et ses conditions de déploiement.

## Solution détaillée

### Nom

`support-ticket-classifier-v1`

### Description

Classifieur supervisé qui attribue une catégorie à un ticket support entrant.

### Usage prévu

- pré-tri des tickets ;
- aide à la priorisation ;
- suggestion de file de traitement.

Le modèle ne doit pas fermer automatiquement un ticket ni refuser une demande client.

### Données

Tickets historiques anonymisés, catégories validées par l'équipe support, période documentée.

### Métriques

```text
accuracy globale
F1 macro
rappel par catégorie critique
taux d'escalade manuelle
```

### Limites

- catégories rares moins bien apprises ;
- dérive possible si les produits changent ;
- sensible aux tickets très courts ;
- peut confondre incident technique et demande commerciale.

### Risques

- mauvais routage d'un ticket critique ;
- biais contre des formulations atypiques ;
- confiance excessive dans une prédiction.

### Seuils de déploiement

```text
rappel catégorie critique >= 0.95
F1 macro >= seuil défini
mode humain obligatoire sous seuil de confiance
```

### Version et propriétaire

```text
version: 1.0
owner: équipe ML/support
date: 2026-06-11
```

## Points importants

- Une model card décrit l'usage prévu et interdit.
- Les métriques par classe sont importantes.
- Les catégories rares doivent être surveillées.
- Le modèle doit avoir un propriétaire.
- Les seuils de déploiement doivent être explicites.

## Prolongement

Une model card doit évoluer avec les données, le modèle et les incidents. Ce n'est pas un document qu'on écrit une fois pour faire joli.
