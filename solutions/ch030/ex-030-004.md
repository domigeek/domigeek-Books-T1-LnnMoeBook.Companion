# EX-030-004 - Flux d'observabilité

## Énoncé

Définissez les événements à journaliser pendant l'exécution d'un orchestrateur LNN + MoE.

## Ce que l'exercice vérifie

L'exercice vérifie que l'observabilité doit être conçue dans l'architecture, pas ajoutée après les incidents.

## Solution détaillée

Événements minimaux :

```text
InputReceived
StateUpdated
ExpertsRanked
ConstraintApplied
ExpertInvoked
ExpertFailed
ResultAggregated
OutputEmitted
```

Chaque événement devrait contenir :

```text
correlationId
timestamp
eventType
source
modelVersion
policyVersion
latencyMs
costEstimate
```

Pour `StateUpdated` :

- état résumé ;
- `Delta t` ;
- norme ou métrique de changement ;
- entrée ayant causé la mise à jour.

Pour `ExpertsRanked` :

- scores de routage ;
- top-k ;
- experts exclus ;
- raison d'exclusion.

Pour `ConstraintApplied` :

- permission ;
- budget ;
- sécurité ;
- fraîcheur mémoire ;
- limite de coût.

Pour `ExpertInvoked` :

- expert ;
- version ;
- entrée résumée ;
- latence ;
- résultat ;
- erreur éventuelle.

## Points importants

- Le `correlationId` relie tout le flux.
- Les scores de routage doivent être visibles.
- Les contraintes appliquées doivent être journalisées.
- Les erreurs experts doivent être distinguées des erreurs routeur.
- Les logs doivent être structurés, pas seulement textuels.

## Prolongement

Une bonne trace doit permettre de rejouer une décision : quelle entrée, quel état, quels experts, quelles contraintes, quel coût, quel résultat.
