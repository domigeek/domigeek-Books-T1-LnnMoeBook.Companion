# EX-037-001 - Estimer le coût de communication d'un expert parallelism jouet

## Énoncé

Supposons `T` tokens, `E` experts, `K` experts actifs par token, `D` appareils et une fraction `r` de dispatchs distants. Écrivez une formule simple pour estimer le nombre d'envois distants et le coût de communication.

## Ce que l'exercice vérifie

L'exercice vérifie que le parallélisme d'experts ne se résume pas à répartir des experts sur plusieurs appareils. Dès qu'un token doit aller vers un expert qui n'est pas local, il faut payer une communication.

## Solution détaillée

Chaque token est envoyé vers `K` experts actifs. Le nombre total de dispatchs logiques est donc :

```text
dispatchs_totaux = T * K
```

Si une fraction `r` de ces dispatchs est distante, le nombre d'envois distants est :

```text
envois_distants = T * K * r
```

Cette formule est volontairement simple. Elle donne un ordre de grandeur. Elle ne tient pas encore compte de la taille des tenseurs, de la latence réseau, du regroupement des messages ni du coût de retour.

Pour estimer le coût de communication, on peut introduire :

```text
B = taille en octets du payload envoyé par token vers un expert
c = coût par octet transféré
l = latence fixe moyenne par message
M = nombre de messages physiques après regroupement
```

Une première approximation :

```text
coût_comm ≈ (T * K * r * B * c) + (M * l)
```

Si l'on veut inclure le retour des sorties d'experts, on peut ajouter un terme de retour :

```text
B_out = taille en octets de la réponse d'expert
coût_comm_total ≈ (T * K * r * B_in * c)
                + (T * K * r * B_out * c)
                + (M_in + M_out) * l
```

Dans un modèle pédagogique plus court, on peut simplifier avec un coût unitaire par dispatch distant :

```text
coût_comm ≈ T * K * r * c_remote
```

Exemple :

```text
T = 4096 tokens
K = 2 experts actifs
r = 0,35
c_remote = 1 unité

envois_distants = 4096 * 2 * 0,35 = 2867,2
coût_comm ≈ 2867 unités
```

Comme on ne peut pas envoyer `0,2` message, une simulation concrète arrondirait selon les dispatchs observés. Mais pour une estimation architecturale, cette valeur dit déjà quelque chose : avec seulement 35 % de dispatchs distants, le nombre d'échanges peut devenir très grand.

Le nombre d'appareils `D` intervient indirectement. Si les experts sont bien placés et que les tokens sont souvent locaux, `r` peut rester faible. Si les experts sont distribués sans affinité avec les données, `r` peut augmenter. Un grand `D` peut aussi augmenter la complexité du regroupement, même si chaque appareil calcule moins.

## Interprétation

La formule montre un point simple :

```text
le coût de communication augmente linéairement avec T et K,
mais il dépend fortement de r.
```

Réduire `K` réduit le nombre d'experts actifs. Réduire `r` améliore la localité. Réduire `B` compresse le payload. Réduire `M` améliore le batching des messages. Ce sont quatre leviers différents.

## Points importants

- `T * K` donne le nombre de décisions d'experts à servir.
- `r` mesure la part de ces décisions qui franchit une frontière d'appareil.
- Le coût réel dépend autant du réseau que du calcul.
- Un placement d'experts mal pensé peut transformer un gain théorique en goulot de communication.

## Prolongement

Une version plus réaliste ajouterait la capacité des experts, les tokens débordés, le regroupement par destination, la taille du hidden state et le temps d'attente induit par les appareils plus lents.
