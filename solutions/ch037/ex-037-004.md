# EX-037-004 - Analyser le simulateur de sharding

## Énoncé

Lisez `ShardingSimulator.cs`. Expliquez la différence entre placement round-robin et placement concentré. Indiquez pourquoi le déséquilibre de charge augmente.

## Ce que l'exercice vérifie

L'exercice vérifie que le placement des experts est un problème d'architecture système. Le même routeur peut produire des coûts très différents selon l'endroit où les experts sont placés.

## Solution détaillée

Dans `ShardingSimulator.cs`, deux stratégies de placement sont utilisées pour rendre le problème visible.

Le placement round-robin distribue les experts sur les appareils :

```text
expert 0 -> device 0
expert 1 -> device 1
expert 2 -> device 2
expert 3 -> device 0
expert 4 -> device 1
...
```

L'idée est simple : ne pas mettre tous les experts au même endroit. La charge potentielle est répartie. Ce placement ne garantit pas une distribution parfaite, car le routeur peut préférer certains experts, mais il évite le pire cas évident.

Le placement concentré place tous les experts sur un seul appareil cible :

```text
expert 0 -> device 0
expert 1 -> device 0
expert 2 -> device 0
expert 3 -> device 0
...
```

Ce placement est volontairement mauvais pour l'exercice. Il permet de montrer ce qui arrive quand la capacité logique du MoE n'est pas alignée avec la capacité matérielle.

Le simulateur calcule plusieurs éléments :

- les tokens originaires de chaque appareil ;
- les experts activés ;
- les dispatchs locaux ou distants ;
- la charge par appareil ;
- le coût de calcul ;
- le coût de communication ;
- un déséquilibre de charge.

Le déséquilibre augmente dans le placement concentré parce que l'appareil qui possède tous les experts reçoit la majorité du calcul expert. Les autres appareils peuvent encore produire des tokens, mais ils doivent envoyer leurs dispatchs vers l'appareil concentrateur. Résultat : un appareil devient le point chaud du système.

On peut résumer ainsi :

```text
round-robin:
  calcul expert réparti
  communication présente
  charge plus équilibrée

concentré:
  calcul expert accumulé sur un appareil
  dispatchs distants nombreux
  goulot central
```

Dans le code, le déséquilibre est généralement calculé comme un ratio entre la charge maximale et la charge moyenne :

```text
imbalance = max(total_cost_per_device) / average(total_cost_per_device)
```

Si tous les appareils travaillent à peu près autant, ce ratio se rapproche de `1`. Si un appareil travaille beaucoup plus que les autres, le ratio augmente.

## Pourquoi ce n'est pas seulement un problème de réseau

Il serait tentant de dire que le placement concentré est mauvais uniquement parce qu'il crée de la communication distante. Ce n'est pas complet.

Il crée deux problèmes :

- plus de communication distante ;
- concentration du calcul expert.

Même avec un réseau très rapide, l'appareil qui héberge tous les experts peut devenir le facteur limitant. Le réseau peut livrer les tokens rapidement, mais il faut encore les traiter.

## Critères d'acceptation

Une bonne réponse doit mentionner :

- le round-robin répartit les experts entre appareils ;
- le concentré place tous les experts sur un même appareil ;
- le déséquilibre augmente parce que le calcul et les dispatchs se concentrent ;
- le coût observé dépend du routage, du placement et de la communication ;
- le simulateur est pédagogique et ne prétend pas reproduire tous les détails d'un cluster réel.

## Points importants

Le placement des experts fait partie du modèle opérationnel. Un MoE sparse peut être élégant sur papier et inefficace en production si ses experts sont mal placés.

## Prolongement

Une version plus réaliste du simulateur pourrait ajouter la capacité maximale par expert, une pénalité pour tokens débordés, une topologie réseau, des affinités entre types de tokens et experts, puis une stratégie de rebalancement dynamique.
