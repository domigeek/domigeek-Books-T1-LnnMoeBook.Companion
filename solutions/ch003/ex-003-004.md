# EX-003-004 - Perte mathématique et objectif réel

## Énoncé

Choisissez une application, proposez une fonction de coût, dites ce qu'elle mesure bien, ce qu'elle rate et quelle métrique complémentaire ajouter.

## Ce que l'exercice vérifie

L'exercice vérifie une distinction critique : la fonction de coût optimise un proxy, pas forcément l'objectif réel du système.

Dans un projet ML, confondre les deux mène souvent à des modèles qui ont de bons chiffres et de mauvais comportements en production.

## Solution détaillée

Prenons une application de classification d'anomalies dans des logs applicatifs.

Le système reçoit une fenêtre de signaux :

```text
erreurs HTTP
latence
timeouts
CPU
mémoire
nombre de requêtes
```

Il doit prédire si la fenêtre correspond à une anomalie.

Une fonction de coût classique est la cross-entropy binaire :

```text
L = - y * log(p) - (1 - y) * log(1 - p)
```

Ici :

- `y` vaut `1` si la fenêtre est une anomalie, sinon `0` ;
- `p` est la probabilité prédite d'anomalie.

### Ce que la perte mesure bien

La cross-entropy mesure si le modèle attribue une forte probabilité à la bonne classe. Elle pénalise fortement les prédictions confiantes et fausses.

Si une fenêtre est vraiment anormale (`y = 1`) et que le modèle prédit `p = 0.01`, la perte est élevée. C'est utile : le système devrait éviter d'être très confiant dans la mauvaise direction.

Elle est aussi différentiable, pratique pour l'entraînement et bien intégrée dans les frameworks.

### Ce que la perte rate

Elle ne mesure pas directement le coût métier.

Dans un système de monitoring, un faux négatif peut coûter très cher : incident non détecté, panne prolongée, perte de données. Un faux positif peut aussi coûter cher : alerte inutile, fatigue opérationnelle, perte de confiance dans le système.

La cross-entropy ne sait pas naturellement que ces coûts sont asymétriques, sauf si on les encode explicitement par pondération ou stratégie de seuil.

Elle ne mesure pas non plus :

- le délai de détection ;
- la stabilité des alertes ;
- la qualité par type d'incident ;
- la dérive dans le temps ;
- l'explicabilité opérationnelle ;
- la charge générée sur les équipes.

### Métriques complémentaires

On peut ajouter :

- précision ;
- rappel ;
- F1-score ;
- courbe precision-recall ;
- délai moyen de détection ;
- taux d'alertes par heure ;
- faux négatifs sur incidents critiques ;
- métrique par service ou par type d'anomalie.

Dans ce cas, le rappel sur incidents critiques peut être plus important que l'accuracy globale. Un modèle qui prédit "pas d'anomalie" presque tout le temps peut avoir une bonne accuracy si les anomalies sont rares. Il serait pourtant mauvais.

Un contrat d'évaluation plus sérieux pourrait être :

```text
minimiser la cross-entropy pendant l'entraînement
mais accepter le modèle seulement si :
  rappel incidents critiques >= 0.95
  faux positifs par service <= seuil défini
  délai médian de détection <= 2 minutes
  performance stable sur une période récente hors entraînement
```

## Points importants

- La perte est un outil d'optimisation.
- L'objectif réel est souvent plus large que la perte.
- Une bonne métrique dépend du coût des erreurs.
- Les classes rares rendent l'accuracy dangereuse.
- Le seuil de décision fait partie du système, pas seulement du modèle.

## Prolongement

Pour une architecture modulaire, on peut séparer :

- perte d'entraînement du modèle ;
- métriques de validation ;
- métriques de production ;
- règles de décision ;
- mécanismes d'alerte ;
- politique de rollback.

C'est une bonne habitude : ne pas demander à une seule fonction mathématique de porter tout le sens métier.
