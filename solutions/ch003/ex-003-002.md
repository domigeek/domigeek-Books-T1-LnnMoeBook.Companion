# EX-003-002 - Diagnostiquer un learning rate

## Énoncé

Pour trois comportements de perte, proposez deux hypothèses possibles : perte lente, perte oscillante, perte train en baisse mais validation en hausse.

## Ce que l'exercice vérifie

L'exercice vérifie un réflexe terrain : une courbe de perte est un signal de diagnostic, pas un verdict automatique.

Même symptôme, causes possibles différentes. Il faut proposer des hypothèses, puis les tester.

## Solution détaillée

### Cas 1 : la perte baisse très lentement

Première hypothèse : le learning rate est trop faible.

Si les pas d'optimisation sont minuscules, le modèle avance dans la bonne direction, mais trop lentement. La courbe descend, mais elle donne l'impression de marcher dans la mélasse.

Vérifications possibles :

- augmenter légèrement le learning rate ;
- observer la norme des gradients ;
- comparer avec un scheduler ;
- faire un court test sur quelques centaines d'itérations.

Deuxième hypothèse : les features ou les entrées sont mal normalisées.

Si certaines dimensions ont des échelles très différentes, l'optimisation peut devenir mal conditionnée. Le modèle n'avance pas avec la même facilité dans toutes les directions.

Vérifications possibles :

- regarder les statistiques des entrées ;
- normaliser les features ;
- vérifier les activations intermédiaires ;
- comparer la perte avant et après normalisation.

### Cas 2 : la perte oscille fortement

Première hypothèse : le learning rate est trop élevé.

Le modèle dépasse régulièrement les zones intéressantes au lieu de s'en approcher. La perte peut descendre, remonter, redescendre, parfois diverger.

Vérifications possibles :

- réduire le learning rate ;
- utiliser un warmup ;
- surveiller la norme des gradients ;
- ajouter du gradient clipping si les gradients explosent.

Deuxième hypothèse : le mini-batch est trop petit ou trop bruité.

Un mini-batch estime le gradient à partir d'un échantillon. Si cet échantillon est trop petit ou très variable, la direction d'optimisation peut changer brutalement d'un pas à l'autre.

Vérifications possibles :

- augmenter la taille de batch si la mémoire le permet ;
- accumuler les gradients ;
- vérifier le mélange des données ;
- observer la perte lissée plutôt que chaque point brut.

### Cas 3 : la perte d'entraînement baisse, mais la validation augmente

Première hypothèse : surapprentissage.

Le modèle apprend de mieux en mieux les exemples d'entraînement, mais généralise moins bien. Il peut mémoriser des détails, du bruit ou des biais spécifiques au train set.

Vérifications possibles :

- ajouter early stopping ;
- réduire la taille du modèle ;
- ajouter régularisation L2 ou dropout ;
- augmenter ou nettoyer les données ;
- vérifier la séparation train/validation.

Deuxième hypothèse : fuite de distribution ou validation mal construite.

La validation peut représenter un régime différent. Dans ce cas, la courbe ne dit pas seulement "le modèle overfit". Elle peut dire : "la validation ne mesure pas la même chose".

Vérifications possibles :

- inspecter les distributions train et validation ;
- vérifier les périodes temporelles ;
- éviter les fuites de données ;
- comparer par sous-groupes ;
- construire une validation plus proche du déploiement réel.

## Points importants

- Une courbe ne donne pas une cause unique.
- Le learning rate trop bas donne souvent une progression lente.
- Le learning rate trop haut donne souvent oscillation ou divergence.
- Train en baisse et validation en hausse signale souvent un problème de généralisation, mais il faut aussi vérifier les données.
- Le diagnostic doit mener à une expérience courte et mesurable.

## Prolongement

Une bonne pratique consiste à tenir un petit journal d'expérience :

```text
hypothèse testée
changement appliqué
métrique observée
résultat
décision suivante
```

Sans ce journal, on finit vite par "tourner des boutons". Et tourner des boutons sans hypothèse, ce n'est pas de l'optimisation. C'est du bricolage coûteux.
