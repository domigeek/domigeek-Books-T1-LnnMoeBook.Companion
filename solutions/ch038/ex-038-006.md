# EX-038-006 - Stratégie de rollback

## Énoncé

Décrire comment revenir d'une version `0.4.0` vers une version `0.3.0` si la latence p95 double après déploiement.

## Ce que l'exercice vérifie

L'exercice vérifie que le rollback d'un modèle ne concerne pas seulement les poids. Il faut restaurer le modèle, la configuration, le runtime, le routage, les dépendances et parfois les données associées.

## Solution détaillée

Le scénario :

```text
version active précédente : 0.3.0
nouvelle version déployée : 0.4.0
incident : latence p95 multipliée par 2
objectif : revenir à 0.3.0 sans perdre la traçabilité
```

La première étape est de confirmer le signal. Il faut vérifier que la hausse p95 n'est pas due à un incident réseau externe, à un pic de trafic ou à une dépendance lente. Mais cette vérification doit être rapide. Si le seuil de rollback est clair, on ne débat pas pendant une heure pendant que les utilisateurs subissent le problème.

Un plan de rollback :

1. Déclencher l'alerte sur la latence p95.
2. Geler la promotion de `0.4.0`.
3. Marquer `0.4.0` comme `degraded` ou `blocked` dans le registre.
4. Réactiver le manifeste `0.3.0`.
5. Restaurer l'artefact modèle `0.3.0`.
6. Restaurer la configuration associée.
7. Restaurer la politique de routage ou les experts associés si le service est MoE.
8. Redémarrer ou recharger les instances selon le mécanisme prévu.
9. Vérifier readiness.
10. Surveiller p50, p95, erreurs et qualité après retour.
11. Conserver les traces de l'incident pour analyse.

Le manifeste de `0.3.0` doit contenir assez d'information pour éviter un rollback incomplet :

```text
model artifact hash
configuration
runtime
router configuration
expert versions
data schema
preprocessing version
postprocessing version
feature flags
```

Si on restaure seulement les poids mais qu'on garde la configuration `0.4.0`, on ne sait pas vraiment ce qui tourne. C'est un demi-rollback, souvent plus dangereux qu'un échec visible.

## Exemple de procédure opérationnelle

```text
Incident:
  moe-service 0.4.0 p95 = 420 ms
  baseline 0.3.0 p95 = 205 ms

Action:
  route traffic from 0.4.0 to 0.3.0
  set model_registry[0.4.0].status = degraded
  load manifest 0.3.0
  verify artifact hash
  restart inference workers
  run readiness checks
  monitor 30 minutes
```

La vérification après rollback est aussi importante que le rollback lui-même. On veut voir :

- p95 revenu près de la baseline ;
- taux d'erreur stable ;
- absence de saturation mémoire ;
- absence de fallback anormal ;
- version active correctement exposée dans `/metadata`.

## Cas MoE

Pour un MoE, il faut vérifier en plus :

- versions des experts ;
- configuration `TopK` ;
- capacité par expert ;
- routeur actif ;
- seuils de fallback ;
- distribution de charge.

Une nouvelle version peut doubler la latence parce qu'elle active plus d'experts, parce qu'un expert est devenu lent, parce que le routeur concentre le trafic, ou parce que le dispatch est moins local. Le rollback doit donc restaurer l'ensemble de la chaîne.

## Points importants

- Le rollback doit être prévu avant l'incident.
- Un manifeste complet rend le rollback fiable.
- Le p95 est souvent plus révélateur que la moyenne.
- Revenir aux poids précédents ne suffit pas toujours.
- La version dégradée doit être bloquée tant qu'elle n'est pas analysée.

## Prolongement

Après l'incident, il faut produire un court post-mortem : cause probable, métriques observées, durée, impact, décision de rollback, correctif prévu et test empêchant la régression.
