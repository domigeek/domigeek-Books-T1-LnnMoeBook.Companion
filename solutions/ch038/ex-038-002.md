# EX-038-002 - Manifeste de modèle

## Énoncé

Concevoir un manifeste de versionnement pour un modèle entraîné sur données synthétiques. Inclure artefact, hash, code commit, données, configuration, runtime, métriques et statut.

## Ce que l'exercice vérifie

L'exercice vérifie que versionner un modèle ne veut pas dire conserver seulement un fichier de poids. Pour pouvoir rejouer, auditer ou restaurer un modèle, il faut savoir d'où il vient et dans quelles conditions il a été produit.

## Solution détaillée

Un manifeste peut être écrit en JSON ou YAML. JSON est pratique pour les outils. YAML est plus lisible à la main. Voici une version JSON :

```json
{
  "schema": "lnn-moe-model-manifest/v1",
  "model": {
    "name": "simple-ltc-synthetic",
    "version": "0.3.0",
    "status": "candidate",
    "createdAtUtc": "2026-06-11T18:30:00Z"
  },
  "artifact": {
    "path": "models/simple-ltc-synthetic/0.3.0/model.bin",
    "sha256": "replace-with-real-sha256",
    "format": "custom-demo",
    "sizeBytes": 18342
  },
  "code": {
    "repository": "LnnMoeBook.Companion",
    "commit": "replace-with-git-commit",
    "branch": "main",
    "dirty": false
  },
  "data": {
    "kind": "synthetic",
    "generator": "SimpleLtcCell.GenerateSyntheticSequences",
    "sequenceCount": 32,
    "sequenceLength": 7,
    "seed": 42,
    "dataHash": "replace-with-data-hash"
  },
  "configuration": {
    "solver": "rk4",
    "internalStepSize": 0.02,
    "iterations": 60,
    "learningRate": 0.22,
    "epsilon": 0.001
  },
  "runtime": {
    "dotnet": "8.0",
    "torchSharp": "replace-with-version",
    "os": "windows",
    "device": "cpu"
  },
  "metrics": {
    "initialLoss": 1.2345,
    "finalLoss": 0.1234,
    "lossReductionRatio": 0.90
  },
  "approval": {
    "approvedForDemo": true,
    "approvedForProduction": false,
    "notes": "Modèle pédagogique entraîné sur données synthétiques."
  }
}
```

Le champ `status` doit être explicite. Par exemple :

```text
draft      -> artefact généré, pas encore évalué
candidate  -> évalué localement, pas encore promu
active     -> version servie
deprecated -> encore disponible, mais à remplacer
blocked    -> version interdite
```

Le champ `artifact.sha256` sert à vérifier que le fichier chargé est bien celui qui a été validé. Le champ `code.commit` sert à retrouver le code exact. Le champ `data` rappelle que même des données synthétiques doivent être décrites : générateur, dimensions, seed et hash.

Le manifeste peut être représenté en C# par un record :

```csharp
public sealed record ModelManifest(
    string Schema,
    ModelInfo Model,
    ArtifactInfo Artifact,
    CodeInfo Code,
    DataInfo Data,
    TrainingConfiguration Configuration,
    RuntimeInfo Runtime,
    MetricInfo Metrics,
    ApprovalInfo Approval);
```

L'important n'est pas la forme exacte du record. L'important est que le service d'inférence puisse charger le manifeste avec le modèle et l'exposer dans `/metadata` ou dans les logs de démarrage.

## Critères d'acceptation

Un manifeste acceptable doit permettre de répondre à ces questions :

- quel fichier de modèle est chargé ?
- son hash correspond-il à la version attendue ?
- quel commit l'a produit ?
- quelles données ont servi à l'entraînement ?
- quelle configuration a été utilisée ?
- quel runtime a servi ?
- quelles métriques ont justifié la promotion ?
- la version est-elle active, candidate ou bloquée ?

## Points importants

Le manifeste est une pièce d'exploitation, pas un luxe documentaire. Sans manifeste, un rollback devient fragile, une comparaison de modèles devient floue et une erreur de déploiement devient difficile à diagnostiquer.

## Prolongement

Pour un système MoE ou modulaire, le manifeste peut aussi lister les experts, leurs versions, leurs hashes, leur politique de routage et leur statut individuel.
