# EX-038-005 - Revue de sécurité

## Énoncé

Lister les principaux risques d'un agent qui peut appeler trois outils externes et accéder à une mémoire vectorielle. Proposer une limite ou un contrôle pour chaque risque.

## Ce que l'exercice vérifie

L'exercice vérifie que l'on traite un agent comme un composant logiciel à permissions bornées. Un agent n'est pas seulement un modèle qui répond. C'est un processus qui peut lire, décider, appeler des outils et produire des effets.

## Solution détaillée

Supposons un agent avec :

- trois outils externes ;
- une mémoire vectorielle ;
- un orchestrateur ;
- un modèle de langage ou module de décision ;
- une API d'entrée.

Voici les principaux risques et les contrôles associés.

| Risque | Description | Contrôle |
|---|---|---|
| Injection d'instructions | Une entrée utilisateur ou un document récupéré tente de modifier les règles de l'agent. | Séparer instructions système, données récupérées et demandes utilisateur ; filtrer les documents ; appliquer une politique d'outil hors du prompt. |
| Appel d'outil non autorisé | L'agent appelle un outil qu'il ne devrait pas utiliser pour cette requête. | Permissions par outil, allowlist par contexte, validation serveur avant exécution. |
| Exfiltration de données | L'agent transmet à un outil externe des données internes ou sensibles. | Classification des données, masquage, blocage de champs sensibles, audit des payloads sortants. |
| Empoisonnement mémoire | Des contenus faux ou malveillants sont ajoutés à la mémoire vectorielle. | Pipeline d'ingestion contrôlé, provenance, score de confiance, quarantaine, révocation. |
| Récupération hors contexte | La mémoire retourne un document proche vectoriellement mais dangereux ou non pertinent. | Filtrage par domaine, date, permission, source et seuil de confiance ; citation de provenance. |
| Boucle d'actions | L'agent répète des appels d'outils sans convergence. | Budget d'étapes, timeout, coût maximal, détection de répétition, arrêt contrôlé. |
| Confusion d'identité ou tenant | Une requête récupère la mémoire d'un autre utilisateur ou client. | Isolation stricte par tenant, vérification d'accès avant récupération, tests d'autorisation. |
| Déni de service économique | L'agent déclenche des appels coûteux ou trop nombreux. | Quotas, rate limits, budgets par requête, coût estimé avant appel. |
| Réponse non traçable | Impossible de savoir quels outils ou mémoires ont influencé la sortie. | Traces structurées, `requestId`, liste d'outils, documents utilisés, versions. |

La règle d'ingénierie est simple : le modèle peut proposer, mais le système doit autoriser. Les permissions ne doivent pas vivre seulement dans une phrase d'instruction. Elles doivent exister dans le code, la configuration et les tests.

## Politique minimale d'appel d'outil

Un appel d'outil devrait passer par un validateur :

```text
demande agent
  -> vérifier outil autorisé
  -> vérifier contexte utilisateur
  -> vérifier classification des données
  -> vérifier budget
  -> exécuter
  -> journaliser
```

Si un outil modifie un état externe, il faut souvent ajouter une confirmation, une simulation ou un mode dry-run.

## Politique minimale de mémoire vectorielle

La mémoire doit être traitée comme une source non parfaite :

```text
retrieval
  -> filtrage permissions
  -> filtrage source
  -> score minimum
  -> limite de documents
  -> provenance visible
  -> exclusion des documents bloqués
```

Une similarité vectorielle n'est pas une preuve de vérité. C'est un signal de proximité.

## Points importants

- Les outils doivent être bornés par des permissions réelles.
- La mémoire doit être filtrée par provenance et droits d'accès.
- Les budgets évitent les boucles et les coûts imprévus.
- Les traces rendent les décisions auditables.
- La sécurité ne doit pas dépendre uniquement du bon comportement du modèle.

## Prolongement

Une revue plus avancée peut ajouter une matrice par outil : action possible, données accessibles, risque maximal, approbation requise, journalisation, rollback et tests d'abus.
