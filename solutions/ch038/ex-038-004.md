# EX-038-004 - Plan d'observabilité

## Énoncé

Écrire un plan d'observabilité pour un service MoE : métriques, logs, traces, événements de routage et alertes.

## Ce que l'exercice vérifie

L'exercice vérifie que les MoE demandent une observabilité spécifique. Surveiller seulement la latence et le taux d'erreur ne suffit pas. Il faut aussi voir ce que fait le routeur et comment les experts sont utilisés.

## Solution détaillée

Un plan d'observabilité doit couvrir quatre niveaux : métriques, logs, traces et événements métier de routage.

### Métriques

Les métriques agrégées doivent répondre rapidement aux questions d'exploitation.

| Métrique | Type | Usage |
|---|---|---|
| `inference_requests_total` | compteur | volume de requêtes |
| `inference_errors_total` | compteur | erreurs par code |
| `inference_latency_ms` | histogramme | p50, p95, p99 |
| `router_latency_ms` | histogramme | coût du routeur |
| `expert_latency_ms{expert}` | histogramme | coût par expert |
| `expert_selection_total{expert}` | compteur | fréquence de sélection |
| `expert_load_ratio{expert}` | jauge | charge relative |
| `fallback_total` | compteur | nombre de fallbacks |
| `tokens_dropped_total` | compteur | tokens refusés ou débordés |
| `model_version_active` | info | version chargée |

Pour un MoE, les métriques par expert sont indispensables. Sans elles, on ne voit pas si un expert reçoit 80 % du trafic pendant que les autres dorment.

### Logs

Les logs doivent rester exploitables et ne pas exposer de données sensibles. Un log d'inférence peut contenir :

```json
{
  "level": "Information",
  "event": "InferenceCompleted",
  "requestId": "req-001",
  "modelVersion": "moe-demo-0.3.0",
  "latencyMs": 42.8,
  "activeExperts": ["expert-temporal", "expert-routing"],
  "fallbackUsed": false,
  "errorCode": null
}
```

Il ne faut pas logger les prompts, documents ou payloads bruts par défaut. Si un mode diagnostic existe, il doit être contrôlé, temporaire et filtré.

### Traces

Une trace distribuée peut découper une requête en spans :

```text
HTTP request
  validate input
  encode input
  route experts
  expert temporal
  expert memory
  aggregate outputs
  postprocess
```

Chaque span doit porter `requestId`, `modelVersion` et éventuellement `correlationId`. Pour un service distribué, cela permet de voir si la latence vient du routeur, d'un expert précis, d'un accès mémoire ou du post-traitement.

### Événements de routage

Les événements de routage sont plus détaillés que les métriques. Ils peuvent être échantillonnés :

```json
{
  "event": "MoeRoutingDecision",
  "requestId": "req-001",
  "tokenCount": 128,
  "topK": 2,
  "selectedExperts": [
    { "expert": "expert-temporal", "weight": 0.71 },
    { "expert": "expert-memory", "weight": 0.29 }
  ],
  "loadBalancingLoss": 0.04,
  "fallbackPolicy": "none"
}
```

Le but n'est pas d'enregistrer chaque détail de chaque token en production normale. Le but est d'avoir assez de signaux pour diagnostiquer une dérive de routage.

### Alertes

| Alerte | Condition |
|---|---|
| Latence p95 élevée | `inference_latency_ms p95` dépasse le seuil pendant 5 minutes |
| Expert saturé | un expert reçoit plus de `x` fois la charge moyenne |
| Expert inutilisé | sélection proche de zéro pendant une longue fenêtre |
| Fallback élevé | hausse brusque de `fallback_total` |
| Tokens débordés | `tokens_dropped_total` supérieur au seuil |
| Erreurs par version | erreurs concentrées sur une version modèle |

## Points importants

Un service MoE doit rendre le routage visible. Sinon, on exploite un système modulaire comme s'il était monolithique. C'est exactement là que les incidents deviennent difficiles à comprendre.

## Prolongement

Pour un service avec mémoire ou outils, le plan peut ajouter des métriques de récupération, de permissions, de budget, de durée d'appel outil et de taux d'annulation.
