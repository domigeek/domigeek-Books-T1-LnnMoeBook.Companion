# EX-038-003 - Readiness et liveness

## Énoncé

Décrire deux endpoints de santé : un pour savoir si le processus est vivant, un autre pour savoir si le service peut vraiment inférer.

## Ce que l'exercice vérifie

L'exercice vérifie que démarré ne veut pas dire prêt. Un processus peut répondre au réseau tout en étant incapable de charger le modèle, d'allouer la mémoire ou d'exécuter une inférence.

## Solution détaillée

Il faut séparer deux endpoints.

Le premier est un endpoint de liveness :

```http
GET /health/live
```

Il répond à la question :

```text
Le processus est-il vivant ?
```

Une réponse possible :

```json
{
  "status": "live",
  "uptimeSeconds": 1842,
  "processId": 4218
}
```

Ce endpoint doit être léger. Il ne doit pas lancer une inférence complète. Il sert au superviseur pour savoir si le processus est bloqué ou mort.

Le deuxième est un endpoint de readiness :

```http
GET /health/ready
```

Il répond à une autre question :

```text
Le service peut-il accepter du trafic d'inférence maintenant ?
```

Une réponse positive :

```json
{
  "status": "ready",
  "modelVersion": "simple-ltc-synthetic-0.3.0",
  "checks": {
    "modelLoaded": true,
    "manifestValid": true,
    "runtimeInitialized": true,
    "memoryAvailable": true,
    "warmupCompleted": true
  }
}
```

Une réponse négative :

```json
{
  "status": "not_ready",
  "modelVersion": "simple-ltc-synthetic-0.3.0",
  "checks": {
    "modelLoaded": true,
    "manifestValid": true,
    "runtimeInitialized": false,
    "memoryAvailable": true,
    "warmupCompleted": false
  },
  "reason": "Runtime TorchSharp non initialisé."
}
```

La différence est capitale en orchestration. Un orchestrateur peut redémarrer un processus qui échoue au liveness. Pour un échec de readiness, il peut simplement retirer l'instance du trafic le temps qu'elle devienne prête.

## Ce que readiness devrait vérifier

Un service d'inférence sérieux devrait au minimum vérifier :

- modèle chargé ;
- manifeste présent et valide ;
- hash de l'artefact correct ;
- runtime initialisé ;
- mémoire suffisante ;
- configuration valide ;
- warmup terminé ;
- dépendances critiques disponibles ;
- version de modèle non bloquée.

Pour un service MoE, on peut ajouter :

- tous les experts requis sont chargés ;
- le routeur est initialisé ;
- les capacités d'experts sont connues ;
- la configuration de fallback est valide.

## Ce qu'il ne faut pas faire

Il ne faut pas faire de `/health` unique qui retourne `200 OK` parce que le serveur HTTP répond. Cela donne une fausse impression de sécurité. Le service peut être vivant et inutilisable.

Il ne faut pas non plus faire une readiness trop lourde appelée toutes les secondes. Si la readiness lance une grosse inférence, elle peut elle-même devenir une charge parasite.

## Points importants

- Liveness : le processus respire.
- Readiness : le service peut travailler.
- Un échec de liveness peut justifier un redémarrage.
- Un échec de readiness doit retirer l'instance du trafic.
- Les deux endpoints doivent être simples, stables et observables.

## Prolongement

Un troisième endpoint peut exposer les métadonnées :

```http
GET /metadata
```

Il peut retourner la version du modèle, le hash, le commit, le runtime et les capacités supportées, sans mélanger ces informations avec les probes de santé.
