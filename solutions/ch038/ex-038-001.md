# EX-038-001 - Contrat API d'inférence

## Énoncé

Définir une requête et une réponse JSON pour un service d'inférence minimal. Inclure au moins : version d'API, identifiant de requête, version de modèle, entrée, options, résultat, latence et erreur structurée.

## Ce que l'exercice vérifie

L'exercice vérifie que déployer un modèle ne consiste pas seulement à exposer une fonction. Une API d'inférence doit être un contrat lisible, versionné, observable et capable d'exprimer les erreurs.

## Solution détaillée

Une requête minimale peut être :

```json
{
  "apiVersion": "v1",
  "requestId": "req-20260611-000001",
  "modelVersion": "lnn-moe-tome1-demo-0.3.0",
  "input": {
    "kind": "sequence",
    "values": [0.12, 0.18, 0.21, 0.19],
    "deltaTimes": [0.05, 0.05, 0.10, 0.20]
  },
  "options": {
    "maxLatencyMs": 200,
    "returnTrace": false,
    "topK": 2
  }
}
```

La réponse de succès :

```json
{
  "apiVersion": "v1",
  "requestId": "req-20260611-000001",
  "modelVersion": "lnn-moe-tome1-demo-0.3.0",
  "result": {
    "prediction": [0.73],
    "confidence": 0.81,
    "metadata": {
      "activeExperts": ["temporal", "stability"],
      "solver": "rk4"
    }
  },
  "latency": {
    "totalMs": 37.4,
    "preprocessMs": 4.1,
    "inferenceMs": 29.8,
    "postprocessMs": 3.5
  },
  "error": null
}
```

La réponse d'erreur :

```json
{
  "apiVersion": "v1",
  "requestId": "req-20260611-000001",
  "modelVersion": "lnn-moe-tome1-demo-0.3.0",
  "result": null,
  "latency": {
    "totalMs": 6.2,
    "preprocessMs": 6.2,
    "inferenceMs": 0.0,
    "postprocessMs": 0.0
  },
  "error": {
    "code": "INVALID_INPUT_SHAPE",
    "message": "input.values et input.deltaTimes doivent avoir la même longueur.",
    "retryable": false,
    "details": {
      "valuesLength": 4,
      "deltaTimesLength": 3
    }
  }
}
```

Le champ `requestId` est essentiel. Sans lui, il devient difficile de relier un appel client, un log serveur, une trace distribuée et une alerte. Le champ `modelVersion` est tout aussi important : une même API peut servir plusieurs versions d'un modèle.

Le champ `options` doit rester borné. Il ne faut pas laisser le client piloter n'importe quel paramètre interne. Dans un service sérieux, certaines options sont acceptées, d'autres sont ignorées ou refusées selon une politique explicite.

Le champ `latency` doit séparer les étapes. Si seule la latence totale est exposée, on ne sait pas si le problème vient de la validation d'entrée, du modèle, du routeur, d'un outil externe ou du post-traitement.

## Critères d'acceptation

Le contrat est acceptable s'il contient :

- une version d'API ;
- un identifiant de requête ;
- une version de modèle ;
- une entrée structurée ;
- des options bornées ;
- un résultat structuré ;
- une latence détaillée ;
- une erreur structurée avec code stable ;
- une distinction claire entre succès et échec.

## Points importants

Une API d'inférence doit être conçue pour l'exploitation. Les champs qui paraissent administratifs au début deviennent indispensables quand il faut diagnostiquer un incident, comparer deux versions ou rejouer une requête.

## Prolongement

Pour un service modulaire ou MoE, on peut ajouter un mode trace contrôlé. Ce mode ne doit pas exposer de données sensibles, mais il peut indiquer les experts activés, les durées par étape et les décisions de fallback.
