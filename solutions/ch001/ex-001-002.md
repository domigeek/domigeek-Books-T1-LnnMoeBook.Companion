# EX-001-002 - Identifier la limite architecturale

## Énoncé

Choisissez une architecture parmi perceptron, RNN, LSTM, Transformer ou MoE, puis expliquez le problème qu'elle exprime mieux, son hypothèse, une limite et une métrique de vérification.

## Ce que l'exercice vérifie

L'exercice vérifie la capacité à lire une architecture comme une hypothèse de travail, et pas comme une solution magique.

Une architecture dit toujours quelque chose du problème :

- ce qu'elle rend facile ;
- ce qu'elle rend coûteux ;
- ce qu'elle suppose implicitement ;
- ce qu'elle mesure mal si on ne fait pas attention.

Voici une solution possible avec le Transformer.

## Solution détaillée

Un Transformer exprime très bien un problème où il faut comparer plusieurs éléments d'un contexte. Son mécanisme d'attention permet à une position de pondérer d'autres positions pour construire sa représentation. C'est utile dans le texte, le code, certains signaux multimodaux et beaucoup de tâches où la relation entre éléments compte plus que leur proximité immédiate.

Le problème qu'il exprime mieux qu'un RNN simple est la dépendance longue portée dans une séquence. Un RNN traite la séquence pas à pas. En théorie, son état caché peut transporter de l'information depuis le début. En pratique, cette information peut être comprimée, diluée ou rendue difficile à entraîner. Le Transformer, lui, permet à une position d'accéder directement aux autres positions de la fenêtre de contexte.

Son hypothèse principale est que beaucoup de relations utiles peuvent être reconstruites par comparaison entre représentations dans une fenêtre donnée. Ce n'est pas une hypothèse absurde : dans une phrase, un token peut dépendre d'un autre token éloigné. Dans du code, une variable peut être déclarée plusieurs lignes avant son usage. Dans un document, une section peut clarifier une autre section.

Mais cette hypothèse a une limite. Le Transformer standard ne modélise pas naturellement le temps continu. Il voit surtout des positions. Deux événements peuvent être voisins dans la séquence, mais séparés par une milliseconde ou par trois semaines. Si cette information temporelle n'est pas encodée correctement, le modèle peut traiter deux situations très différentes comme structurellement proches.

Une autre limite est le coût. L'attention dense a un coût qui croît fortement avec la longueur du contexte. Cela ne veut pas dire que les Transformers sont mauvais. Cela veut dire que leur force - comparer beaucoup d'éléments - devient aussi leur point de pression.

Une métrique de vérification doit donc dépendre de ce qu'on veut tester.

Si on veut tester la capacité de dépendance longue portée :

- on peut mesurer l'exactitude sur des tâches où l'information utile est éloignée ;
- on peut varier la distance entre indice et cible ;
- on peut comparer avec un RNN, un LSTM ou un SSM sur la même tâche.

Si on veut tester le coût :

- on mesure la latence par longueur de contexte ;
- l'utilisation mémoire ;
- le débit en tokens par seconde ;
- le coût par requête.

Si on veut tester une hypothèse temporelle :

- on construit des données où l'espacement temporel change ;
- on compare un modèle sans information de temps, un modèle avec encodage de temps et un modèle conçu pour traiter des observations irrégulières.

Le point important est que la métrique doit attaquer l'hypothèse, pas seulement produire un chiffre confortable.

## Points importants

- Une architecture est un compromis, pas une vérité générale.
- Dire "le Transformer est meilleur" ne veut rien dire sans tâche, métrique et budget.
- Le Transformer exprime très bien les relations dans une fenêtre de contexte.
- Il n'exprime pas naturellement tous les phénomènes temporels continus.
- Une bonne évaluation doit tester la limite autant que la force.

## Prolongement

Le même raisonnement peut être appliqué à un MoE.

Un MoE exprime l'idée que tous les tokens ou toutes les situations ne nécessitent pas les mêmes transformations. Son hypothèse est qu'une spécialisation d'experts peut améliorer le rapport capacité/coût. Sa limite est le routage : si le routeur s'effondre, surcharge certains experts ou apprend une spécialisation artificielle, le système peut devenir instable. Les métriques pertinentes incluent alors l'utilisation par expert, la perte d'équilibrage, les tokens rejetés, la qualité par sous-domaine et le coût actif.
