# EX-001-003 - Relier histoire et architecture modulaire

## Énoncé

Dessinez un schéma reliant quatre idées historiques du chapitre à des préoccupations modernes comme mémoire temporelle, routage, temps continu ou modularité.

## Ce que l'exercice vérifie

L'exercice demande moins un beau dessin qu'une carte d'architecture. Le but est de relier des idées historiques à des problèmes qui reviennent dans les systèmes modernes.

Une bonne réponse doit montrer :

- les idées historiques retenues ;
- le problème moderne associé ;
- ce que l'idée éclaire ;
- ce qu'elle ne suffit pas à résoudre.

## Solution détaillée

Voici une réponse possible sous forme de schéma textuel.

```text
McCulloch-Pitts
  -> neurone formel, calcul logique
  -> graphes computationnels modernes
  -> limite : pas d'apprentissage dans la formulation de base

Hebb
  -> adaptation locale des connexions
  -> plasticité, apprentissage local, mémoire associative
  -> limite : pas un protocole complet d'optimisation supervisée moderne

Rosenblatt
  -> perceptron entraînable
  -> couches linéaires, classification, optimisation de paramètres
  -> limite : séparation linéaire

RNN
  -> état caché récurrent
  -> mémoire temporelle, traitement séquentiel, dynamique d'état
  -> limite : gradients difficiles, mémoire compressée

MoE moderne
  -> spécialisation de modules
  -> routage, experts, coût actif, modularité
  -> limite : équilibrage, collapse, observabilité
```

On peut ensuite convertir cette carte en contrat d'architecture :

| Idée historique | Préoccupation moderne | Responsabilité | Limite à surveiller |
|---|---|---|---|
| Neurone formel | Graphe de calcul | Transformer des entrées en sorties selon une règle | Ne dit rien sur l'apprentissage |
| Hebb | Adaptation | Modifier des connexions selon l'activité | Peut renforcer des corrélations inutiles |
| Perceptron | Apprentissage supervisé | Ajuster des poids pour séparer des classes | Ne résout pas les frontières non linéaires complexes |
| RNN | Mémoire temporelle | Maintenir un état à travers une séquence | Peut oublier ou dégrader les dépendances longues |
| MoE | Modularité spécialisée | Activer des experts pertinents | Peut mal router ou déséquilibrer les experts |

Dans une vraie architecture logicielle, on ne se contenterait pas de dessiner des flèches. On ajouterait des critères d'observation.

Pour la mémoire temporelle :

- longueur effective de dépendance ;
- stabilité de l'état ;
- sensibilité aux séquences longues ;
- comportement en cas de données irrégulières.

Pour le routage :

- distribution des tokens par expert ;
- entropie du routeur ;
- taux de surcharge ;
- qualité par sous-domaine ;
- latence de dispatch.

Pour la modularité :

- contrat d'entrée/sortie de chaque module ;
- version des experts ;
- métriques par expert ;
- stratégie de fallback ;
- coût actif par requête.

Le schéma doit donc éviter deux pièges. Le premier est de faire croire que les anciennes idées expliquent directement toute l'IA moderne. Ce serait trop simple. Le second est de croire qu'elles sont dépassées. Elles restent utiles parce qu'elles posent les questions de base : calcul, apprentissage, mémoire, adaptation, spécialisation.

## Points importants

- Une carte historique doit montrer des filiations, pas des équivalences parfaites.
- La modularité moderne ajoute des problèmes système : routage, monitoring, versions, latence, coûts.
- Une idée peut être fondatrice sans être suffisante.
- Le bon schéma distingue responsabilité, limite et métrique.

## Prolongement

Pour aller plus loin, on peut refaire le même exercice avec les chapitres du tome :

```text
Perceptron -> MLP -> Backpropagation -> RNN/LSTM/GRU
          -> Transformers -> SSM/LNN -> MoE -> architectures modulaires
```

Cette chaîne montre une chose importante : l'histoire ne va pas seulement vers "plus gros". Elle va vers des formes d'organisation plus adaptées à certains problèmes.
