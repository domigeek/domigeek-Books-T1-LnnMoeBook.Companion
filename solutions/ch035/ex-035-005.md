# EX-035-005 - Définir un cycle de vie d'expert dynamique

## Énoncé

Décrivez les conditions pour créer, tester, promouvoir, geler, fusionner ou retirer un expert.

## Ce que l'exercice vérifie

L'exercice vérifie qu'un expert dynamique doit avoir un cycle de vie gouverné. La flexibilité n'autorise pas l'improvisation invisible.

## Solution détaillée

### Créer

Créer un expert si :

- un nouveau régime de tâche apparaît ;
- les experts existants échouent de manière répétée ;
- les métriques montrent un sous-domaine mal couvert ;
- assez de données existent pour évaluer l'expert.

### Tester

Tester en sandbox :

- dataset dédié ;
- scénarios rejouables ;
- comparaison avec experts existants ;
- latence ;
- coût ;
- stabilité.

### Promouvoir

Promouvoir si :

```text
gain qualité clair
pas de régression critique
coût acceptable
observabilité complète
rollback possible
```

### Geler

Geler si :

- comportement instable ;
- dérive ;
- incident ;
- manque de données ;
- conflit avec politique.

### Fusionner

Fusionner deux experts si :

- fonctions redondantes ;
- routage indiscernable ;
- même couverture ;
- coût inutile.

### Retirer

Retirer si :

- expert jamais utilisé ;
- performance inférieure aux baselines ;
- risque sécurité ;
- coût injustifié ;
- remplacement validé.

## Points importants

- Un expert dynamique a besoin d'un registre.
- La promotion doit exiger métriques et rollback.
- Le gel protège le système.
- La fusion réduit la dette.
- Le retrait doit être traçable.

## Prolongement

Dans une architecture modulaire ambitieuse, la création d'experts peut être dynamique, mais la gouvernance doit rester stricte. Sinon, le système accumule des modules impossibles à expliquer.
