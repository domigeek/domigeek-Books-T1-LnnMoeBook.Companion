# EX-011-002 - Attention et causalité

## Énoncé

Donnez un exemple où deux événements sont fortement associés dans une séquence, mais où cette association ne suffit pas à démontrer une causalité.

## Ce que l'exercice vérifie

L'exercice vérifie une prudence essentielle : association, attention élevée ou proximité temporelle ne prouvent pas une relation causale.

Un modèle peut repérer une régularité utile sans connaître la cause réelle du phénomène.

## Solution détaillée

Prenons un système de monitoring.

On observe souvent la séquence suivante :

```text
CPU élevé -> latence API élevée
```

Ces deux événements peuvent être fortement associés dans les logs. Pourtant, cette association ne suffit pas à dire que le CPU élevé cause la latence.

Plusieurs explications sont possibles :

1. Le CPU élevé cause effectivement la latence.
2. La latence cause indirectement plus de retries, ce qui augmente le CPU.
3. Les deux sont causés par un troisième facteur, par exemple une base de données lente.
4. Les deux apparaissent ensemble pendant les pics de trafic, sans relation directe simple.
5. La corrélation est un artefact de mesure ou de sampling.

Si un Transformer accorde beaucoup d'attention au token ou à l'événement `CPU élevé`, cela peut indiquer que ce signal aide la prédiction. Mais cela ne prouve pas que le CPU est la cause.

Pour parler de causalité, il faudrait des éléments plus solides :

- expériences contrôlées ;
- interventions ;
- contre-factuels ;
- analyse temporelle rigoureuse ;
- connaissances système ;
- tests de perturbation ;
- reproduction sur plusieurs contextes.

Dans un incident réel, un architecte ne devrait donc pas dire :

```text
le modèle a regardé CPU, donc CPU est la cause
```

Il devrait dire :

```text
CPU est un signal associé à la prédiction. Il faut vérifier la chaîne causale avec des traces système et des tests.
```

## Points importants

- Corrélation ne veut pas dire causalité.
- L'ordre temporel aide, mais ne suffit pas.
- L'attention indique une contribution au calcul, pas une preuve de cause.
- Une cause commune peut expliquer deux événements associés.
- Les systèmes réels demandent des traces, des interventions et des contre-vérifications.

## Prolongement

Cette prudence sera importante dans les architectures agentiques et modulaires. Un système peut produire une explication plausible, mais une explication plausible n'est pas automatiquement une explication vraie.
